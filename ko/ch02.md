# 2 FreeRTOS 커널 배포판 (The FreeRTOS Kernel Distribution)

<a id="21-introduction"></a>
## 2.1 개요 (Introduction)

독자가 FreeRTOS 커널 파일과 디렉터리 구성을 쉽게 파악할 수 있도록, 이 장에서는 다음 내용을 다룬다.

- FreeRTOS 디렉터리 구조의 최상위 뷰를 제공한다.
- 특정 FreeRTOS 프로젝트를 구성할 때 필요한 소스 파일들을 설명한다.
- 데모 애플리케이션을 소개한다.
- 새로운 FreeRTOS 프로젝트를 생성하는 방법을 안내한다.

여기서 다루는 설명은 공식 FreeRTOS 배포판만을 기준으로 한다. 이 책에 부속된 예제들은 이와 약간 다른 구성을 사용한다.

<a id="22-understanding-the-freertos-distribution"></a>
## 2.2 FreeRTOS 배포판의 이해 (Understanding the FreeRTOS Distribution)

<a id="221-definition-freertos-port"></a>
### 2.2.1 정의: FreeRTOS 포트 (Definition: FreeRTOS Port)

FreeRTOS는 약 20종류의 서로 다른 컴파일러로 빌드할 수 있으며, 40종 이상의 다양한 프로세서 아키텍처에서 동작할 수 있다. 지원되는 컴파일러와 프로세서의 조합 각각을 **FreeRTOS port(포트)**라고 부른다.

<a id="222-building-freertos"></a>
### 2.2.2 FreeRTOS 빌드 (Building FreeRTOS)

FreeRTOS는 본래 단일 스레드(single-threaded) 베어메탈(bare-metal) 애플리케이션이었을 프로그램에 멀티태스킹 기능을 부여하는 라이브러리다.

FreeRTOS는 C 소스 파일 세트로 제공된다. 일부 소스 파일은 모든 포트에서 공통으로 사용되며, 다른 일부는 특정 포트에 종속적이다. 프로젝트의 일부로 소스 파일들을 빌드하면 애플리케이션에서 FreeRTOS API를 사용할 수 있게 된다. 공식적으로 지원되는 각 FreeRTOS 포트마다 참고용으로 활용할 수 있는 데모 애플리케이션이 함께 제공된다. 이 데모 애플리케이션은 올바른 소스 파일들을 빌드하고 알맞은 헤더 파일들을 인클루드하도록 미리 구성되어 있다.

제작 당시 기준으로 각 데모 애플리케이션은 컴파일러 오류나 경고 없이 '즉시(out of the box)' 빌드되도록 작성되었다. 이후 빌드 도구의 버전 변경 등으로 인해 정상적으로 빌드되지 않는 경우가 발생하면 FreeRTOS 지원 포럼(<https://forums.FreeRTOS.org>)을 통해 알려주기 바란다. 2.3절에서는 데모 애플리케이션에 대해 자세히 설명한다.

<a id="223-freertosconfigh"></a>
### 2.2.3 FreeRTOSConfig.h (FreeRTOSConfig.h)

`FreeRTOSConfig.h`라는 헤더 파일에 정의된 상수들을 통해 커널을 구성한다. 소스 파일에서 `FreeRTOSConfig.h`를 직접 인클루드해서는 안 된다! 대신 `FreeRTOS.h`를 인클루드해야 하며, 그러면 적절한 시점에 `FreeRTOS.h`가 `FreeRTOSConfig.h`를 자동으로 인클루드한다.

`FreeRTOSConfig.h`는 특정 애플리케이션의 요구에 맞게 FreeRTOS 커널을 맞춤 설정(tailor)하는 데 사용된다. 예를 들어 `FreeRTOSConfig.h`에는 FreeRTOS가 협력형(co-operative) 스케줄링을 사용할지 선점형(pre-emptive) 스케줄링을 사용할지 정의하는 `configUSE_PREEMPTION`과 같은 상수가 포함되어 있다[^1].

[^1]: 4.13절에서 스케줄링 알고리즘을 자세히 다룬다.

`FreeRTOSConfig.h`는 특정 애플리케이션 전용으로 FreeRTOS를 설정하는 파일이므로, FreeRTOS 소스 코드가 들어 있는 디렉터리가 아니라 반드시 애플리케이션 디렉터리의 일부로 위치해야 한다.

공식 FreeRTOS 배포판에는 모든 FreeRTOS 포트에 대응하는 데모 애플리케이션이 들어 있으며, 각 데모 애플리케이션마다 고유한 `FreeRTOSConfig.h` 파일이 포함되어 있다. 파일을 처음부터 새로 만들기보다는, 사용하려는 FreeRTOS 포트용 데모 애플리케이션에 제공된 `FreeRTOSConfig.h`를 시작점으로 삼아 필요한 부분을 수정해 나가는 방식을 권장한다.

`FreeRTOSConfig.h`에 등장하는 상수들에 대한 설명은 FreeRTOS 레퍼런스 매뉴얼 및 <https://www.freertos.org/a00110.html> 에서 확인할 수 있다. `FreeRTOSConfig.h`에 모든 상수를 일일이 명시할 필요는 없으며, 생략된 상수는 대다수 기본값이 적용된다.

<a id="224-official-distributions"></a>
### 2.2.4 공식 배포판 (Official Distributions)

커널을 포함한 개별 FreeRTOS 라이브러리는 자체 GitHub 저장소 및 ZIP 아카이브 파일 형태로 각각 내려받을 수 있다. 양산용 제품 코드에 FreeRTOS를 적용할 때는 이렇게 개별 라이브러리 단위로 내려받는 방식이 편리하다. 그러나 FreeRTOS를 처음 시작할 때는 라이브러리와 예제 프로젝트를 모두 포함하고 있는 공식 통합 배포판을 다운로드하는 것이 좋다.

공식 통합 배포판에는 모든 FreeRTOS 라이브러리의 소스 코드, 모든 FreeRTOS 커널 포트, 그리고 모든 FreeRTOS 데모 애플리케이션을 위한 프로젝트 파일이 들어 있다. 파일 개수가 방대하다고 해서 위축될 필요는 없다! 실제 애플리케이션에서 필요한 것은 이 중 극히 일부에 불과하다.

최신 배포판이 포함된 ZIP 파일은 <https://github.com/FreeRTOS/FreeRTOS/releases/latest> 에서 다운로드할 수 있다. 또는 다음 Git 명령 중 하나를 사용하여 GitHub에서 각 라이브러리가 서브모듈(submodule)로 포함된 메인 배포판을 통째로 clone할 수도 있다.

```
git clone git@github.com:FreeRTOS/FreeRTOS.git --recurse-submodules
```

<a id="225-freertos-source-files-common-to-all-ports"></a>
### 2.2.5 모든 포트 공통 FreeRTOS 소스 파일 (FreeRTOS Source Files Common to All Ports)

`tasks.c`와 `list.c`는 FreeRTOS 커널의 핵심 기능을 구현하며 언제나 필수적으로 요구된다. 이 두 파일은 그림 2.2에 나타난 바와 같이 `FreeRTOS/Source` 디렉터리에 바로 위치한다. 동일한 디렉터리에는 다음과 같은 선택적(optional) 소스 파일들도 들어 있다.

- **queue.c**

  이 책의 후반부에서 설명하듯이 `queue.c`는 queue(큐)와 semaphore(세마포어) 서비스를 모두 제공한다. `queue.c`는 거의 항상 프로젝트에 포함되어야 한다.

- **timers.c**

  `timers.c`는 software timer(소프트웨어 타이머) 기능을 제공한다. 애플리케이션에서 software timer를 사용할 때만 빌드 대상에 포함하면 된다.

- **event_groups.c**

  `event_groups.c`는 event group(이벤트 그룹) 기능을 제공한다. 애플리케이션에서 event group을 사용할 때만 빌드 대상에 포함하면 된다.

- **stream_buffer.c**

  `stream_buffer.c`는 스트림 버퍼(stream buffer)와 메시지 버퍼(message buffer) 기능을 모두 제공한다. 애플리케이션에서 스트림 버퍼나 메시지 버퍼를 사용할 때만 빌드 대상에 포함하면 된다.

- **croutine.c**

  `croutine.c`는 FreeRTOS 코루틴(co-routine) 기능을 구현한다. 애플리케이션에서 코루틴을 사용할 때만 빌드하면 된다. 코루틴은 매우 작은 마이크로컨트롤러 환경을 위해 고안된 것으로, 현재는 거의 사용되지 않는다. 따라서 더 이상 유지보수되지 않으며, 새로운 설계에는 사용을 권장하지 않는다. 이 책에서는 코루틴을 다루지 않는다.

```
└─Source
    │
    ├─tasks.c         FreeRTOS source file - always required
```

ZIP 파일 배포판에서 사용된 파일 이름들은 이미 많은 프로젝트에서 동일한 이름을 사용할 수 있으므로 네임스페이스 충돌을 유발할 수 있다. 사용자는 필요한 경우 파일 이름을 변경할 수 있지만, 공식 배포판 자체의 파일 이름을 변경할 수는 없다. 그렇게 할 경우 기존 사용자 프로젝트는 물론 FreeRTOS 지원 개발 도구들과의 호환성이 깨지기 때문이다.

<a id="226-freertos-source-files-specific-to-a-port"></a>
### 2.2.6 특정 포트 전용 FreeRTOS 소스 파일 (FreeRTOS Source Files Specific to a Port)

`FreeRTOS/Source/portable` 디렉터리에는 특정 FreeRTOS 포트에 종속적인 소스 파일들이 들어 있다. portable 디렉터리는 먼저 컴파일러별로, 그 다음 프로세서 아키텍처별로 계층화되어 정리되어 있다. 그림 2.3은 이러한 계층 구조를 보여준다.

컴파일러 '*compiler*'를 사용하여 아키텍처 '*architecture*'의 프로세서에서 FreeRTOS를 실행하려면, 핵심 FreeRTOS 소스 파일 외에도 `FreeRTOS/Source/portable/[compiler]/[architecture]` 디렉터리에 위치한 파일들을 함께 빌드해야 한다.

3장 'heap(힙) 메모리 관리(Heap Memory Management)'에서 다루듯이, FreeRTOS는 heap 메모리 할당 체계 또한 포터블 계층(portable layer)의 일부로 취급한다. 만약 `configSUPPORT_DYNAMIC_ALLOCATION`이 0으로 설정되어 있다면 프로젝트에 heap 메모리 할당 구현을 포함하지 말아야 한다.

FreeRTOS는 `FreeRTOS/Source/portable/MemMang` 디렉터리에 예제 heap 할당 체계들을 제공한다. FreeRTOS가 동적 메모리 할당을 사용하도록 구성된 경우라면, 해당 디렉터리에 있는 heap 구현 소스 파일 중 하나를 프로젝트에 포함하거나 독자적인 heap 구현을 직접 제공해야 한다.

> **! 프로젝트에 예제 heap 할당 구현을 둘 이상 포함해서는 안 된다.**

<a name="fig2.3" title="Figure 2.3 Port specific source files within the FreeRTOS directory tree"></a>

* * *
```

│
└─Source
    │
    └─portable Directory containing all port specific source files
        │
        ├─MemMang Directory containing the alternative heap allocation source files
        │
        ├─[compiler 1] Directory containing port files specific to compiler 1
        │   │
        │   ├─[architecture 1] Contains files for the compiler 1 architecture 1 port
        │   ├─[architecture 2] Contains files for the compiler 1 architecture 2 port
        │   └─[architecture 3] Contains files for the compiler 1 architecture 3 port
        │
        └─[compiler 2] Directory containing port files specific to compiler 2
            │
            ├─[architecture 1] Contains files for the compiler 2 architecture 1 port
            ├─[architecture 2] Contains files for the compiler 2 architecture 2 port
            └─[etc.]
```

<a id="227-include-paths"></a>
### 2.2.7 인클루드 경로 (Include Paths)

FreeRTOS는 컴파일러의 인클루드 경로(include path)에 다음 세 개의 디렉터리를 포함할 것을 요구한다.

1. 핵심 FreeRTOS 커널 헤더 파일들이 위치한 경로: `FreeRTOS/Source/include`
2. 사용 중인 FreeRTOS 포트 전용 소스 파일들이 위치한 경로: `FreeRTOS/Source/portable/[compiler]/[architecture]`
3. 해당 프로젝트의 올바른 `FreeRTOSConfig.h` 헤더 파일이 위치한 경로

<a id="228-header-files"></a>
### 2.2.8 헤더 파일 (Header Files)

FreeRTOS API를 사용하는 소스 파일은 반드시 `FreeRTOS.h`를 가장 먼저 인클루드해야 하며, 그 뒤에 사용하려는 API 함수의 원형(prototype)이 정의된 헤더 파일(`task.h`, `queue.h`, `semphr.h`, `timers.h`, `event_groups.h`, `stream_buffer.h`, `message_buffer.h`, `croutine.h` 중 하나)을 인클루드해야 한다. 그 밖의 다른 FreeRTOS 헤더 파일들을 명시적으로 인클루드해서는 안 된다. `FreeRTOS.h`가 `FreeRTOSConfig.h`를 자동으로 인클루드한다.

<a id="23-demo-applications"></a>
## 2.3 데모 애플리케이션 (Demo Applications)

각 FreeRTOS 포트에는 제작 당시 기준으로 컴파일러 오류나 경고 없이 즉시 빌드되는 사전 구성된 데모 애플리케이션이 최소 하나 이상 함께 제공된다. 이후 빌드 도구의 버전 변경으로 인해 정상적으로 빌드되지 않는 경우가 발생하면 FreeRTOS 지원 포럼(<https://forums.FreeRTOS.org>)을 통해 알려주기 바란다.

> **크로스 플랫폼 지원 (Cross Platform Support)**: FreeRTOS는 Windows, Linux, macOS 환경과 임베디드 및 전통적인 다양한 툴체인에서 개발되고 테스트된다. 그러나 버전 차이나 누락된 테스트로 인해 간혹 빌드 오류가 발생할 수 있다. 이러한 오류를 발견하면 FreeRTOS 지원 포럼(<https://forums.FreeRTOS.org>)을 통해 제보해주기 바란다.

데모 애플리케이션은 다음과 같은 몇 가지 중요한 목적을 갖는다.

- 올바른 파일들이 인클루드되고 올바른 컴파일러 옵션이 설정된, 실제 동작하는 사전 구성 프로젝트의 모범 예시를 제공한다.
- 최소한의 설정과 사전 지식만으로 즉시 실습과 실험을 진행할 수 있게 한다.
- FreeRTOS API의 올바른 사용법을 시연한다.
- 실제 상용 애플리케이션을 개발할 때 출발점이 되는 베이스 역할을 한다.
- 커널 구현의 스트레스 테스트(stress test)를 수행한다.

각 데모 프로젝트는 `FreeRTOS/Demo` 디렉터리 아래의 고유한 하위 디렉터리에 위치한다. 하위 디렉터리의 이름은 해당 데모 프로젝트가 어느 포트와 관련되어 있는지를 나타낸다.

FreeRTOS.org 공식 웹사이트에는 각 데모 애플리케이션에 대한 안내 페이지가 마련되어 있다. 해당 웹 페이지에는 다음 정보들이 포함되어 있다.

- FreeRTOS 디렉터리 구조 내에서 해당 데모의 프로젝트 파일을 찾는 방법
- 프로젝트가 사용하도록 구성된 타깃 하드웨어 또는 에뮬레이터 정보
- 데모를 실행하기 위한 하드웨어 설정 방법
- 데모 빌드 방법
- 데모의 예상 동작(expected behaviour)

모든 데모 프로젝트는 '공통 데모 task(common demo tasks)'의 일부를 생성하며, 그 구현 코드는 `FreeRTOS/Demo/Common/Minimal` 디렉터리에 있다. 공통 데모 task들은 FreeRTOS API의 사용법을 보여주고 FreeRTOS 커널 포트를 테스트하기 위한 목적으로 존재하며, 특정하게 유용한 실제 기능을 구현하지는 않는다.

많은 데모 프로젝트는 통상 2개의 RTOS task와 1개의 queue를 생성하는 단순한 '블링키(blinky)' 형태의 입문용 스타터 프로젝트로 동작하도록 구성할 수도 있다.

모든 데모 프로젝트에는 `main()` 함수가 정의된 `main.c` 파일이 포함되어 있으며, `main()` 함수는 FreeRTOS 커널을 시작하기 전에 데모 애플리케이션 task들을 생성한다. 개별 데모에 특화된 자세한 정보는 각 `main.c` 파일 내부의 주석을 참조하기 바란다.

## 2.4 FreeRTOS 프로젝트 생성 (Creating a FreeRTOS Project)

<a id="241-adapting-one-of-the-supplied-demo-projects"></a>
### 2.4.1 제공된 데모 프로젝트 변형 활용 (Adapting One of the Supplied Demo Projects)

모든 FreeRTOS 포트에는 최소 하나 이상의 사전 구성된 데모 애플리케이션이 함께 제공된다. 새로운 프로젝트를 생성할 때는 이렇게 이미 존재하는 데모 프로젝트 중 하나를 변형하여 시작하는 방식을 권장한다. 그래야 새 프로젝트에 올바른 파일들이 포함되고, 올바른 인터럽트 핸들러가 설치되며, 올바른 컴파일러 옵션이 빠짐없이 설정될 수 있기 때문이다.

기존 데모 프로젝트를 기반으로 새 애플리케이션을 생성하는 절차는 다음과 같다.

1. 제공된 데모 프로젝트를 열고 예상대로 정상 빌드 및 실행되는지 확인한다.
2. 데모 task들을 구현하는 소스 파일들(`Demo/Common` 디렉터리에 위치한 파일들)을 프로젝트에서 제거한다.
3. 코드 2.1에 표시된 바와 같이, `main()` 함수 내부에서 `prvSetupHardware()`와 `vTaskStartScheduler()`를 제외한 모든 함수 호출을 삭제한다.
4. 프로젝트가 여전히 정상적으로 빌드되는지 확인한다.

이 단계를 따르면 올바른 FreeRTOS 소스 파일들을 포함하면서도 아직 아무런 고유 기능이 정의되지 않은 깨끗한 프로젝트가 완성된다.

<a name="list2.1" title="Listing 2.1 The template for a new main() function"></a>

```c
int main( void )
{
    /* Perform any hardware setup necessary. */
    prvSetupHardware();

    /* --- APPLICATION TASKS CAN BE CREATED HERE --- */

    /* Start the created tasks running. */
    vTaskStartScheduler();

    /* Execution will only reach here if there was insufficient heap to
       start the scheduler. */
    for( ;; );
    return 0;
}
```

### 2.4.2 처음부터 새 프로젝트 생성하기 (Creating a New Project from Scratch)

앞서 언급했듯이 기존 데모 프로젝트를 기반으로 새 프로젝트를 생성하는 편이 바람직하다. 만약 이러한 방식을 원치 않는다면 다음 절차에 따라 프로젝트를 처음부터 생성한다.

1. 선택한 툴체인을 사용하여 아직 FreeRTOS 소스 파일이 포함되지 않은 빈 프로젝트를 새로 생성한다.
2. 새 프로젝트가 정상적으로 빌드되고 타깃 하드웨어에 다운로드되어 실행되는지 확인한다.
3. 정상 동작하는 프로젝트 기반이 마련되었음을 확인한 후에만 표 1에 명시된 FreeRTOS 소스 파일들을 프로젝트에 추가한다.
4. 사용 중인 포트용 데모 프로젝트에서 사용된 `FreeRTOSConfig.h` 헤더 파일을 새 프로젝트 디렉터리로 복사한다.
5. 프로젝트가 헤더 파일을 탐색할 경로(include path)에 다음 디렉터리들을 추가한다.
   - `FreeRTOS/Source/include`
   - `FreeRTOS/Source/portable/[compiler]/[architecture]` (여기서 `[compiler]`와 `[architecture]`는 선택한 포트에 맞는 경로여야 함)
   - `FreeRTOSConfig.h` 헤더 파일이 들어 있는 디렉터리
6. 관련 데모 프로젝트로부터 컴파일러 설정을 복사하여 적용한다.
7. 필요한 FreeRTOS 인터럽트 핸들러를 설치한다. 사용 중인 포트에 대한 웹 안내 페이지와 해당 포트용으로 제공된 데모 프로젝트를 참고자료로 활용한다.

## 2.5 데이터 타입과 코딩 스타일 가이드 (Data Types and Coding Style Guide)

<a id="251-data-types"></a>
### 2.5.1 데이터 타입 (Data Types)

FreeRTOS의 각 포트에는 포트 고유의 `portmacro.h` 헤더 파일이 존재하며, 이 헤더 파일에는 (다른 여러 정의와 함께) 특정 포트에 특화된 두 가지 데이터 타입인 `TickType_t`와 `BaseType_t`에 대한 정의가 들어 있다. 다음 목록은 사용되는 매크로 또는 typedef와 실제 데이터 타입을 설명한다.

- `TickType_t`

  FreeRTOS는 tick(틱) 인터럽트(tick interrupt(tick 인터럽트))라는 주기적인 인터럽트를 구성한다.

  FreeRTOS 애플리케이션이 시작된 이후 발생한 tick 인터럽트의 총 횟수를 **tick count(누적 tick 값)**라고 부른다. tick count는 시간의 측정 단위로 사용된다.

  두 tick 인터럽트 사이의 시간 간격을 **tick period(tick 주기)**라고 부른다. 시간은 tick period의 배수로 지정된다.

  `TickType_t`는 tick count 값을 보관하고 시간을 지정하는 데 사용되는 데이터 타입이다.

  `TickType_t`는 `FreeRTOSConfig.h`의 `configTICK_TYPE_WIDTH_IN_BITS` 설정에 따라 부호 없는 16비트 타입, 부호 없는 32비트 타입, 또는 부호 없는 64비트 타입이 될 수 있다. `configTICK_TYPE_WIDTH_IN_BITS` 설정은 아키텍처에 종속적이다. FreeRTOS 포트는 이 설정값이 유효한지도 검사한다.

  16비트 타입을 사용하면 8비트 및 16비트 아키텍처에서 효율성을 대폭 개선할 수 있지만, FreeRTOS API 호출에서 지정할 수 있는 최대 대기 시간(maximum block time)이 크게 제한된다. 32비트 또는 64비트 아키텍처에서 16비트 `TickType_t` 타입을 사용할 이유는 없다.

  이전에 사용되던 `configUSE_16_BIT_TICKS`는 32비트보다 큰 tick count를 지원하기 위해 `configTICK_TYPE_WIDTH_IN_BITS`로 대체되었다. 새로운 설계에서는 `configUSE_16_BIT_TICKS` 대신 `configTICK_TYPE_WIDTH_IN_BITS`를 사용해야 한다.

<a name="tbl2" title="Table 2 TickType_t data type and the configTICK_TYPE_WIDTH_IN_BITS configuration"></a>

* * *
| configTICK_TYPE_WIDTH_IN_BITS | 8비트 아키텍처 | 16비트 아키텍처 | 32비트 아키텍처 | 64비트 아키텍처 |
| :--- | :--- | :--- | :--- | :--- |
| `TICK_TYPE_WIDTH_16_BITS` | `uint16_t` | `uint16_t` | `uint16_t` | 해당 없음(N/A) |
| `TICK_TYPE_WIDTH_32_BITS` | `uint32_t` | `uint32_t` | `uint32_t` | 해당 없음(N/A) |
| `TICK_TYPE_WIDTH_64_BITS` | 해당 없음(N/A) | 해당 없음(N/A) | `uint64_t` | `uint64_t` |

- `BaseType_t`

  해당 아키텍처에서 가장 효율적인 데이터 타입으로 항상 정의된다. 일반적으로 64비트 아키텍처에서는 64비트 타입, 32비트 아키텍처에서는 32비트 타입, 16비트 아키텍처에서는 16비트 타입, 8비트 아키텍처에서는 8비트 타입으로 정의된다.

  `BaseType_t`는 일반적으로 매우 제한된 범위의 값만을 갖는 반환 타입이나 `pdTRUE`/`pdFALSE` 같은 불리언(Boolean) 타입에 사용된다.

<a id="252-variable-names"></a>
### 2.5.2 변수 이름 명명 규칙 (Variable Names)

변수 이름 앞에는 데이터 타입을 나타내는 접두사가 붙는다. `char`는 'c', `int16_t`(short)는 's', `int32_t`(long)는 'l', `BaseType_t` 및 기타 비표준 타입(구조체, task 핸들, queue 핸들 등)에는 'x'가 붙는다.

변수가 부호 없는(unsigned) 타입인 경우 접두사 앞에 'u'가 추가된다. 변수가 포인터인 경우 접두사 앞에 'p'가 추가된다. 예를 들어 `uint8_t` 타입 변수 앞에는 'uc'가 붙고, char 포인터(`char *`) 타입 변수 앞에는 'pc'가 붙는다.

<a id="253-function-names"></a>
### 2.5.3 함수 이름 명명 규칙 (Function Names)

함수 이름 앞에는 반환 타입과 해당 함수가 정의된 소스 파일명을 나타내는 접두사가 함께 붙는다. 예를 들면 다음과 같다.

- `vTaskPrioritySet()`은 *v*oid를 반환하며 **tasks**.c 파일 내에 정의되어 있다.
- `xQueueReceive()`는 *BaseType_t* 타입 변수를 반환하며 **queue**.c 파일 내에 정의되어 있다.
- `pvTimerGetTimerID()`는 *v*oid 포인터(*p*)를 반환하며 **timers**.c 파일 내에 정의되어 있다.

파일 스코프를 갖는 비공개(private) 함수 이름 앞에는 'prv'가 붙는다.

<a id="254-formatting"></a>
### 2.5.4 서식 (Formatting)

일부 데모 애플리케이션에서는 탭(tab)이 사용되며, 탭 1개는 항상 공백 4개와 동일하게 설정된다. 커널 자체 소스 코드에서는 더 이상 탭을 사용하지 않는다.

<a id="256-rationale-for-excessive-type-casting"></a>
### 2.5.6 과도한 형변환의 배경 (Rationale for Excessive Type Casting)

FreeRTOS 소스 코드는 수많은 서로 다른 컴파일러로 컴파일되며, 컴파일러마다 경고(warning)를 생성하는 조건과 방식이 제각각이다. 특히 컴파일러마다 캐스팅(casting)을 요구하는 방식이 서로 다르다. 그 결과 FreeRTOS 소스 코드에는 통상적으로 정당화될 수 있는 수준보다 더 많은 타입 캐스팅이 포함되어 있다.
