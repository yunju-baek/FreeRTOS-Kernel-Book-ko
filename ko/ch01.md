# 1 머리말 (Preface)

## 1.1 소형 임베디드 시스템에서의 멀티태스킹 (Multitasking in Small Embedded Systems)

<a id="111-about-the-freertos-kernel"></a>
### 1.1.1 FreeRTOS 커널 소개 (About the FreeRTOS Kernel)

FreeRTOS는 실시간 커널(real-time kernel)과 상호 보완적인 기능을 구현하는 모듈형 라이브러리 집합으로 구성된 C 라이브러리 모음이다.

FreeRTOS는 리처드 배리(Richard Barry)가 2003년경 처음 개발했다. 리처드가 설립한 회사인 Real-Time Engineers Ltd는 2016년 아마존 웹 서비스(Amazon Web Services, AWS)가 FreeRTOS의 운영과 관리를 맡기 전까지 세계 유수의 반도체 기업들과 긴밀히 협력하며 FreeRTOS 개발을 이어왔다. 현재 리처드는 AWS IoT 팀의 시니어 수석 엔지니어(Senior Principal Engineer)로서 FreeRTOS 관련 업무를 계속 수행하고 있다. FreeRTOS는 MIT 라이선스가 적용된 오픈소스 코드이며, 어떤 목적으로든 자유롭게 사용할 수 있다. AWS의 고객이 아니더라도 AWS의 운영 관리 지원 혜택을 온전히 누릴 수 있다.

FreeRTOS 커널은 마이크로컨트롤러나 소형 마이크로프로세서에서 실행되는 심층 임베디드(deeply embedded) 실시간 애플리케이션에 적합하다. 이러한 유형의 애플리케이션에는 통상적으로 hard real-time(경성 실시간) 요구조건과 soft real-time(연성 실시간) 요구조건이 함께 섞여 있다.

연성 실시간 요구조건은 시간 마감 시한(deadline)을 명시하지만, 해당 마감 시한을 넘기더라도 시스템이 완전히 무용지물이 되지는 않는다. 예를 들어 키보드 입력에 대한 응답이 너무 느리면 사용자가 답답함을 느낄 수는 있지만 시스템 자체가 사용 불가능해지는 것은 아니다.

반면 경성 실시간 요구조건은 엄격한 시간 마감 시한을 규정하며, 마감 시한을 넘기면 시스템의 치명적인 실패(absolute failure)로 이어진다. 예를 들어 충돌 센서의 입력에 차량 운전석 에어백이 너무 느리게 반응한다면 승객을 보호하기는커녕 오히려 더 큰 위해를 끼칠 수 있다.

FreeRTOS 커널은 FreeRTOS 기반 애플리케이션이 이러한 경성 실시간 요구조건을 만족할 수 있도록 지원하는 실시간 커널 또는 실시간 scheduler(스케줄러)이다. 애플리케이션을 상호 독립적인 여러 개의 실행 스레드(thread) 집합으로 구조화할 수 있게 해준다. 예를 들어 코어가 하나뿐인 프로세서에서는 특정 시점에 오직 하나의 실행 스레드만 실행될 수 있다. 커널은 애플리케이션 설계자가 각 스레드에 할당한 우선순위(priority)를 검사하여 어느 스레드를 실행할지 결정한다. 가장 단순한 경우라면, 애플리케이션 설계자는 경성 실시간 요구조건을 구현하는 스레드에 더 높은 우선순위를 할당하고 연성 실시간 요구조건을 구현하는 스레드에는 더 낮은 우선순위를 할당할 수 있다. 이러한 방식으로 우선순위를 배정하면 경성 실시간 스레드가 항상 연성 실시간 스레드보다 앞서 실행되도록 보장할 수 있지만, 우선순위 할당 결정이 언제나 그렇게 단순한 것만은 아니다.

앞 단락에서 언급한 개념들을 아직 완전히 이해하지 못했더라도 걱정할 필요는 없다. 이어지는 여러 장에서 다양한 예제와 함께 상세한 설명을 제공하여 실시간 커널, 특히 FreeRTOS의 활용 방법을 체계적으로 이해할 수 있도록 돕는다.

<a id="112-value-proposition"></a>
### 1.1.2 핵심 가치와 이점 (Value Proposition)

FreeRTOS 커널이 전 세계적으로 전례 없는 성공을 거둘 수 있었던 배경에는 확실한 가치 제안이 있다. FreeRTOS는 전문적으로 개발되고 엄격한 품질 관리를 거치며, 견고하고 지속적인 기술 지원을 제공받는다. 지적재산권(IP) 소유권에 모호함이 없으며, 독점 소스 코드를 공개할 의무 없이 상업용 애플리케이션에 완전히 무료로 사용할 수 있다. 나아가 AWS의 운영 관리는 글로벌 입지, 전문적인 보안 이벤트 대응 절차, 대규모의 다양한 개발팀, 정형 검증(formal verification), 모의 침투 테스트(penetration testing), 메모리 안전성 증명(memory safety proofs), 장기 지원(LTS)을 제공한다. 이 모든 과정에서 FreeRTOS는 특정 하드웨어, 개발 도구, 클라우드 서비스에 종속되지 않는 중립적인 오픈소스 프로젝트로 유지된다. FreeRTOS의 개발은 GitHub에서 투명하게 커뮤니티 주도로 이루어지며, 특수한 도구나 독점적인 개발 관행을 요구하지 않는다.

어떠한 수수료도 낼 필요가 없을 뿐 아니라 개발팀에 알릴 필요조차 없이 FreeRTOS를 사용하여 제품을 시장에 출시할 수 있으며, 실제로 수천 개의 기업이 그렇게 제품을 출시하고 있다. 만약 추가적인 기술 보증을 받고 싶거나 법무팀에서 서면 보증 또는 배상 보장(indemnification)을 요구하는 경우, FreeRTOS의 전략적 파트너사들이 합리적인 비용의 간소한 상용 라이선스 옵션을 제공한다. 언제든지 필요할 때 상용 라이선스를 선택할 수 있다는 점은 확고한 안정감을 준다.

<a id="113-a-note-about-terminology"></a>
### 1.1.3 용어에 관한 안내 (A Note About Terminology)

FreeRTOS에서는 각각의 실행 스레드를 'task(태스크)'라고 부른다. 임베디드 커뮤니티 전반에 합의된 단일 표준 용어는 없지만, 일부 애플리케이션 분야에서 thread가 더 특정한 의미를 가질 수 있기 때문에 필자는 'thread'보다 'task'를 선호한다.

<a id="114-why-use-an-rtos"></a>
### 1.1.4 왜 RTOS를 사용하는가? (Why Use an RTOS?)

멀티스레딩 커널을 사용하지 않고도 훌륭한 임베디드 소프트웨어를 작성할 수 있는 검증된 기법은 많다. 개발 중인 시스템이 단순하다면 이러한 기법들이 가장 적절한 해법이 될 수 있다. 시스템이 더 복잡해질수록 커널을 사용하는 편이 바람직하겠지만, 그 전환점이 정확히 어디인지는 항상 주관적일 수밖에 없다.

앞서 설명했듯이 task 우선순위 지정을 통해 애플리케이션의 처리 마감 시한 준수를 보장할 수 있지만, 커널은 이 밖에도 겉으로 잘 드러나지 않는 여러 가지 이점을 제공한다. 그중 일부를 아래에 간략히 나열한다.

- 타이밍 정보의 추상화 (Abstracting away timing information)

  RTOS가 실행 타이밍을 전담하고 애플리케이션에는 시간 관련 API를 제공한다. 그 덕분에 애플리케이션 코드 구조가 훨씬 단순해지고 전체 코드 크기도 줄어든다.

- 유지보수성과 확장성 (Maintainability/Extensibility)

  타이밍 세부 사항을 추상화하면 모듈 간 상호 의존성이 줄어들어 소프트웨어를 통제 가능하고 예측 가능한 방식으로 발전시킬 수 있다. 또한 커널이 타이밍을 담당하므로 하부 하드웨어가 변경되더라도 애플리케이션 성능이 받는 영향이 적다.

- 모듈화 (Modularity)

  각 task는 독립적인 모듈이며, 각각 명확하게 정의된 목적을 가져야 한다.

- 팀 개발 용이성 (Team development)

  task 간 인터페이스를 명확하게 정의할 수 있으므로 팀 단위 개발이 수월해진다.

- 손쉬운 테스트 (Easier testing)

  깔끔한 인터페이스를 갖춘 명확하고 독립적인 모듈로 구성된 task는 개별 격리 테스트를 수행하기가 훨씬 쉽다.

- 코드 재사용성 (Code reuse)

  모듈성이 뛰어나고 상호 의존성이 적도록 설계된 코드는 재사용하기 쉽다.

- 효율성 향상 (Improved efficiency)

  RTOS를 사용하는 애플리케이션 코드는 완전한 이벤트 기반(event-driven)으로 동작할 수 있다. 발생하지도 않은 이벤트를 폴링(polling)하느라 처리 시간을 낭비할 필요가 없다.

  이벤트 기반 구조를 통해 얻는 효율성의 이점과 맞바꾸어야 하는 비용으로는 RTOS의 tick(틱) 인터럽트(tick interrupt(tick 인터럽트))를 처리하고 task 간 실행 권한을 전환(context switch)하는 오버헤드가 있다. 그러나 RTOS를 사용하지 않는 애플리케이션이라 하더라도 보통 어떤 형태로든 tick 인터럽트를 포함하게 마련이다.

- 유휴 시간 활용 (Idle time)

  처리가 필요한 애플리케이션 task가 없을 때는 자동으로 생성되는 idle task(유휴 task)가 실행된다. idle task는 여유 처리 용량을 측정하거나, 백그라운드 검사를 수행하거나, 프로세서를 저전력 모드로 전환하는 데 활용할 수 있다.

- 전력 관리 (Power Management)

  RTOS 사용으로 인한 효율성 향상 덕분에 프로세서가 저전력 모드에 머무를 수 있는 시간이 늘어난다.

  idle task가 실행될 때마다 프로세서를 저전력 상태로 진입시키면 전력 소비를 대폭 줄일 수 있다. FreeRTOS는 특수한 tickless(tick-less) 모드도 지원한다. tickless 모드를 활용하면 프로세서가 일반적인 경우보다 더 깊은 저전력 모드로 진입하여 더 오랜 시간 동안 저전력 상태를 유지할 수 있다.

- 유연한 인터럽트 처리 (Flexible interrupt handling)

  인터럽트 후속 처리를 애플리케이션 작성자가 생성한 task나 자동으로 생성되는 RTOS daemon task(데몬 task, timer task라고도 함)로 지연(defer)시킴으로써 인터럽트 핸들러를 매우 짧게 유지할 수 있다.

- 복합 처리 요구조건의 충족 (Mixed processing requirements)

  단순한 설계 패턴을 적용하여 하나의 애플리케이션 안에서 주기적 처리, 연속 처리, 이벤트 기반 처리를 조화롭게 구성할 수 있다. 또한 적절한 task 및 인터럽트 우선순위를 선택함으로써 경성 실시간 및 연성 실시간 요구조건을 모두 충족할 수 있다.

<a id="115-freertos-kernel-features"></a>
### 1.1.5 FreeRTOS 커널의 주요 기능 (FreeRTOS Kernel Features)

FreeRTOS 커널은 다음과 같은 표준 기능을 제공한다.

- 선점형(pre-emptive) 또는 협력형(co-operative) 스케줄링 동작
- 선택적 시분할(time-slicing)
- 매우 유연한 task 우선순위 할당
- 유연하고 빠르며 가벼운 task notification(task 알림) 메커니즘
- queue(큐)
- binary semaphore(이진 세마포어)
- counting semaphore(계수 세마포어)
- mutex(뮤텍스)
- recursive mutex(재귀 뮤텍스)
- software timer(소프트웨어 타이머)
- event group(이벤트 그룹)
- stream buffer(스트림 버퍼)
- message buffer(메시지 버퍼)
- 코루틴(co-routines, 사용 권장되지 않음/deprecated)
- Tick hook 함수
- Idle hook 함수
- Stack overflow 검사
- Trace 매크로
- Task 실행 시간 통계 수집
- 상용 라이선스 및 기술 지원 옵션
- 완전한 인터럽트 중첩(interrupt nesting) 모델 (일부 아키텍처 지원)
- 초저전력 애플리케이션을 위한 tickless(tick-less) 기능 (일부 아키텍처 지원)
- task 격리 및 애플리케이션 안전성 향상을 위한 메모리 보호 장치(MPU, Memory Protection Unit) 지원 (일부 아키텍처 지원)
- 적절한 경우 소프트웨어 관리형 인터럽트 stack(스택) 지원 (RAM 절약 지원)
- 정적(static) 또는 동적(dynamic) 메모리 할당을 통한 RTOS 객체 생성 기능

<a id="116-licensing-and-the-freertos-openrtos-and-safertos-family"></a>
### 1.1.6 라이선스와 FreeRTOS, OpenRTOS, SafeRTOS 제품군 (Licensing, and The FreeRTOS, OpenRTOS, and SafeRTOS Family)

**FreeRTOS**의 MIT 오픈소스 라이선스는 다음 사항을 보장하도록 설계되었다.

- FreeRTOS를 상업용 애플리케이션에 사용할 수 있다.

- FreeRTOS 자체는 모든 사람에게 언제나 무료로 제공된다.

- FreeRTOS 사용자는 자신의 지적재산권(IP)에 대한 소유권을 온전히 유지한다.

최신 오픈소스 라이선스 정보는 <https://www.FreeRTOS.org/license> 에서 확인할 수 있다.

**OpenRTOS**는 아마존 웹 서비스(AWS)의 라이선스 하에 제3자(파트너사)가 제공하는 FreeRTOS의 상용 라이선스 버전이다.

**SafeRTOS**는 FreeRTOS와 동일한 사용 모델을 공유하지만, 국제적으로 공인된 다양한 기능 안전(safety) 관련 표준 규격을 준수하기 위해 요구되는 엔지니어링 실무, 절차 및 프로세스에 따라 개발된 버전이다.

### 1.2.1 교재 부속 예제 구하기 (Obtaining the Examples that Accompany this Book)

<https://www.FreeRTOS.org/Documentation/code> 에서 다운로드할 수 있는 ZIP 파일에는 이 책에서 다루는 예제들을 빌드하고 실행하는 데 필요한 모든 소스 코드, 사전 구성된 프로젝트 파일 및 안내 지침이 포함되어 있다. 단, 이 ZIP 파일에 반드시 최신 버전의 FreeRTOS가 포함되어 있는 것은 아니다.

이 책에 수록된 스크린샷들은 FreeRTOS Windows port(포트)를 사용하여 Microsoft Windows 환경에서 실행되는 예제의 모습을 보여준다. FreeRTOS Windows port를 사용하는 프로젝트는 <https://www.visualstudio.com/> 에서 다운로드할 수 있는 Visual Studio의 무료 Community 버전을 사용하여 빌드할 수 있도록 미리 구성되어 있다. FreeRTOS Windows port는 편리한 평가, 테스트 및 개발 플랫폼을 제공하지만, 엄밀한 의미의 진정한 실시간(true real-time) 동작을 제공하지는 *않는다*는 점에 유의해야 한다.
